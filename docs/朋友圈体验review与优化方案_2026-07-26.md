# 穿越朋友圈体验 Review 与优化方案

> 审阅范围：`pages/discover/moments`、`pages/discover/moment-detail`、`components/figure-avatar`、`cloudfunctions/moment` 及现有技术方案。  
> 目标：以微信原生朋友圈的熟悉感为交互骨架，用“历史人物正在发动态”的内容差异化来建立沉浸感；不是把页面完全做成微信的复制品。

## 一、结论

当前页面已具备封面、信息流、点赞、评论与详情页的基础轮廓，但还没有形成可用的“朋友圈闭环”。最优先的问题并非样式，而是**前端和云函数协议不一致**：真实接口返回后，列表、详情、点赞和评论均不能按现有页面逻辑正常工作，开发环境会由 mock 数据掩盖该问题。

在体验层面，人物头像目前依赖通用第三方图标，评论者多数没有头像；历史人物身份、内容配图、图片浏览、评论回复和操作反馈都不完整。因此用户会感到它更像“带古风标签的动态列表”，而不是微信语境下可信、可互动的朋友圈。

建议按以下优先级推进：先修通数据与交互闭环（P0），再统一头像与朋友圈信息层级（P1），最后补齐内容表达和沉浸式互动（P2）。

## 二、现状与问题清单

| 优先级 | 问题 | 现象与证据 | 用户影响 | 建议 |
|---|---|---|---|---|
| P0 | 列表接口协议不匹配 | 页面按 `data.moments` 取值并传 `page/pageSize`；云函数 `list` 返回数组 `data`，接收 `limit/lastId`，且没有 `moments` 字段。见 `moments.js`、`cloudfunctions/moment/index.js`。 | 线上返回被判空后回退 mock；分页状态也不可信。 | 定义唯一的 BFF 返回契约：`{ moments, nextCursor, hasMore }`，前端改用 cursor 分页。 |
| P0 | 详情、取消点赞、发布评论动作不存在 | 前端调用 `detail`、`unlike`、`comment`；云函数只实现 `list`、`like`（内部切换）、`commentCreate` 等。 | 详情必然回退 mock；取消点赞和评论不会写入真实数据。 | 统一动作命名。推荐保留 `like`（toggle）和 `commentCreate`，前端据此调用；新增 `detail`。 |
| P0 | 列表字段不一致 | 页面渲染 `figureName`、内嵌 `comments`；云函数提供的是 `authorName/authorAvatar`，评论另存 `moment_comments`。 | 真实人物名、头像、评论气泡会缺失。 | 在云函数的 view model 中统一输出 `figureName`、`avatar`、`likes`、`commentPreview`、`commentCount`，不要让页面猜字段。 |
| P0 | 评论安全与身份不完整 | 列表页的 modal 评论只更新本地，未调内容审核/云函数；详情页虽调用审核，但用户 `name/avatar` 写死为空。 | 刷新即丢；无法追溯作者资料；不符合 UGC 审核要求。 | 所有写评论仅走云函数；服务端从 `users` 读取昵称、头像，前端不传身份；失败时回滚 optimistic UI。 |
| P0 | 点赞并发逻辑有风险 | `toggleLike` 先读后以数据库命令更新，返回结果不含最新点赞列表；前端本地写入“我”。 | 多人同时操作会出现计数与名单短暂不一致；刷新后跳变。 | 点赞单独建 `moment_likes`（`momentId + _openid` 唯一）或在事务中切换；返回最终 `liked/likeCount/likePreview`。 |
| P1 | 人物头像缺失，且风格不统一 | 信息流使用 icons8 通用图标；详情页虽使用 `figure-avatar`，该组件也会优先显示通用 emperor fallback；评论头像仅是姓名首字。 | 历史人物没有辨识度，产品的核心世界观被削弱。 | 建立人物头像资产与映射；动态发布者、点赞者、评论者共用同一 `figure-avatar` 组件与 fallback 策略。 |
| P1 | 现有头像组件有可用性缺陷 | `size="100"` 没有对应 CSS 尺寸；`fallback` 永远有值，首字/朝代色 fallback 永远不会显示。 | 详情头像尺寸不可控；资源失败时不能优雅降级。 | 改为枚举尺寸（`sm/md/lg/xl`），补 `binderror` 状态；无图时显示“姓名首字 + 朝代色”，而非通用图标。 |
| P1 | 朋友圈封面不稳定且缺少身份感 | 头图使用运行时文本生图 URL；名称、头像压在图上，但没有专属封面、发布入口的用户状态。 | 弱网/生成失败会白屏或样式跳变；用户个人空间不可信。 | 上传静态默认封面到云存储；允许用户选图并裁切；头像右下覆盖封面，名称靠头像左侧，保持微信的熟悉布局。 |
| P1 | 信息流未渲染动态图片 | 数据结构已有 `images`，页面没有九宫格、预览或图片比例策略。 | 历史事件的画面感缺失，内容密度单一。 | 增加 1/2/3/4/9 图规则，`lazy-load` + `wx.previewImage`；图像使用云存储缩略图。 |
| P1 | 操作菜单位置与触发反馈偏离原生 | 菜单固定 `top: 90rpx`，不随每条内容高度/屏幕边缘调整；图标为自制两点按钮。 | 菜单可能遮挡正文或超出屏幕，触发目标偏小且不直观。 | 将“更多”锚定 footer，使用三点图标；菜单从按钮左侧弹出，含赞/评论两项，按当前状态切换；点击后立即播放轻量反馈。 |
| P1 | 评论体验断裂 | 列表页使用 `wx.showModal`，详情页是固定单行输入；均不支持回复某条评论。 | 与微信用户习惯不一致，难形成讨论。 | 使用页底跟随键盘的评论输入条；点击评论进入回复态（“回复 张良”），支持取消、@回复关系、失败重试。 |
| P1 | 详情页与列表是两套视觉语言 | 详情页采用大头像、金色渐变事件卡、Emoji 心形、绿色标题条；列表是近微信灰底蓝名。 | 从列表进入详情有明显“换产品”感。 | 详情沿用朋友圈卡片规则：同一头像、蓝色姓名、正文与九宫格、灰色互动框；“史实卡”作为可折叠附加内容。 |
| P1 | 点击区域和导航语义不完整 | 列表只允许点正文进详情；作者头像/名字不可进入人物页；顶部相机仅 toast。 | 用户找不到人物关系和有效操作，功能看起来像半成品。 | 头像/名称进入人物详情；整条动态（排除操作菜单）可进详情；相机进入发布页或在未开放时隐藏，避免“开发中”入口。 |
| P2 | 没有朝代筛选与发现路径 | 原技术方案明确了朝代横向筛选，当前页面未实现。 | 内容越多越难探索，人物宇宙无法建立。 | 封面下加入“全部 / 先秦 / 秦汉 / 三国 / 唐 / 宋 / 明清”横滑筛选，状态吸顶，筛选切换保留滚动与加载状态。 |
| P2 | 历史标签只是静态文本 | `historicalEvent` 仅以金色小字显示，未关联人物、文章或原典。 | 历史内容不能从娱乐自然导向深度阅读。 | 将其改为轻量“史实出处”卡：事件、年代、可信度/说明，点击跳转看一看文章或兰台相应人物/章节。 |
| P2 | 状态反馈不足 | 无首屏骨架、图片加载态、发布/评论失败重试、网络错误态；`loading` 时没有区分首次与分页。 | 弱网下跳动、空白，用户不知道是否成功。 | 增加封面与动态骨架屏、底部分页状态、错误重试按钮；所有乐观更新使用 pending/rollback 状态。 |
| P2 | 无隐私与治理策略 | `visibility` 字段虽存在但未生效；未见删除入口、举报、内容审核状态和评论管理。 | 上线后存在社区治理与隐私风险。 | 明确产品是否“人物官方动态 + 用户仅评论”。若允许用户发动态，补可见范围、删除、举报、审核中/拒绝状态和隐私说明。 |

## 三、目标交互方案

### 1. 信息架构

```text
朋友圈
├─ 我的封面（封面图 / 昵称 / 头像）
├─ 朝代筛选（横滑、选中后吸顶）
├─ 动态流
│  ├─ 人物头像 + 姓名（进入人物页）
│  ├─ 正文 + 展开/收起
│  ├─ 九宫格图片（预览）
│  ├─ 史实出处卡（可跳深度内容）
│  ├─ 时间 / 地点 / 更多菜单
│  └─ 互动气泡（赞 + 评论预览）
└─ 发布入口（仅在发布能力上线后展示）

动态详情
├─ 与列表一致的动态主体
├─ 完整点赞名单
├─ 评论列表（支持回复、长按自己的评论删除）
└─ 跟随键盘的输入栏
```

### 2. 关键交互与微信对齐原则

| 场景 | 推荐行为 | 与现状的差异 |
|---|---|---|
| 头像/姓名 | 点击进入人物页；长按可展示人物名片（P2）。 | 当前无跳转。 |
| 正文 | 超过 6 行折叠，点击“全文”展开；整条动态可打开详情。 | 当前仅正文可点，无折叠。 |
| 图片 | 1 图按原比例上限展示；2–9 图固定网格；点击预览并支持滑动。 | 当前完全未渲染。 |
| 更多菜单 | 点击 3 点，菜单在按钮左侧弹出，只有赞和评论；已赞显示“取消”。 | 当前固定定位，易遮挡。 |
| 点赞 | 先更新按钮、计数和昵称预览；请求失败回滚并提示“操作未成功”。 | 当前无失败回滚，服务端动作不匹配。 |
| 评论 | 点击评论或某一评论均可聚焦输入栏；后者显示回复对象。 | 当前 modal 与详情输入条割裂。 |
| 发布 | 未上线前不展示相机入口；上线后进入“选择图片—编辑—位置/可见范围—发布”。 | 当前点击仅提示“开发中”。 |
| 历史信息 | 默认简洁呈现“鸿门宴 · 前 206”；详情中可展开史实出处。 | 当前金色标签与微信基线割裂。 |

### 3. 视觉规格（建议值）

- 基调：保留微信朋友圈的白/浅灰界面和 `#576B95` 人名链接色；古风只用于头像资产和“史实出处”弱点缀，避免金色渐变、Emoji 与原生样式抢层级。
- 布局：内容区左右 24rpx；头像 84rpx 方圆角（与列表保持一致）；头像与正文间距 20rpx；动态项纵向间距使用 24rpx 的 8rpx 倍数体系。
- 正文：30rpx、行高 1.5；姓名 30rpx/600；时间与地点 24rpx；评论 26rpx。保持正文是第一视觉层级。
- 互动气泡：`#F7F7F7` 背景、轻微 6rpx 圆角，名字蓝色、正文深灰；三角应指向“更多”按钮所在的右侧。
- 可访问性：不只用红/绿区分点赞状态；所有触控目标至少 88rpx；头像、图片和图标要提供可理解的文字语义；图片高对比度下仍能辨识。

## 四、头像资产方案

### 1. 数据模型

以 `figures` 集合为唯一人物资料源，动态中可冗余快照字段以保证历史内容稳定：

```json
{
  "figureId": "liubang",
  "figureName": "刘邦",
  "figureTitle": "汉高祖",
  "avatar": "cloud://.../figures/liubang/avatar_v1.webp",
  "avatarVersion": 1,
  "dynasty": "han"
}
```

- 人物头像：优先使用已授权的统一风格半身像或头像插画；方形 1:1，建议源图 512 × 512，CDN 输出 96/192/384 三档 WebP。
- 用户头像：遵循微信用户授权与隐私说明；没有授权时显示昵称首字 + 中性背景，不冒用默认男性图标。
- 组件：`figure-avatar` 应支持 `src`、`name`、`dynasty`、`size`、`shape`、`binderror`；图片加载失败后切换到首字 fallback。删除默认的外部 icons8 fallback，避免网络依赖及风格割裂。
- 点赞预览：微信式文本名单不需要小头像；“全部赞”页或长按名单时才展示头像列表，降低信息流噪声。

### 2. 资产生产与验收

1. 先建立 20–30 位高频人物清单（刘邦、项羽、张良、诸葛亮、刘备、关羽、张飞、李白、杜甫、苏轼等）。
2. 为每人准备统一 prompt/画风、身份核验、版权来源、缩略图路径和版本号。
3. 导入云存储后，将 `figures.mini_avatar_url/avatar_url` 归一为 `avatar`，保留旧字段兼容迁移期。
4. 在低网速、头像 404、姓名为空三种场景测试 fallback；任何一项都不得显示破图或空白。

## 五、数据与接口改造

### 1. 推荐的前端 view model

列表和详情都消费同一个 `MomentView`，避免页面各自转换字段：

```js
{
  _id: 'm1',
  figure: { id: 'liubang', name: '刘邦', title: '汉高祖', avatar: 'cloud://...', dynasty: 'han' },
  content: '...',
  images: [],
  historical: { event: '鸿门宴', date: '公元前206年', articleId: '', chapterId: '' },
  location: '',
  createdAt: 0,
  displayTime: '2小时前',
  interaction: {
    liked: false,
    likeCount: 3,
    likePreview: [{ id: 'fan_kuai', name: '樊哙' }],
    commentCount: 3,
    commentPreview: []
  }
}
```

### 2. 云函数契约

| Action | 入参 | 成功返回 | 说明 |
|---|---|---|---|
| `list` | `cursor`, `limit`, `dynasty` | `{ moments, nextCursor, hasMore }` | 固定按 `createdAt/_id` 游标分页，不使用 `skip`。 |
| `detail` | `momentId` | `{ moment }` | 返回完整评论首屏及互动状态。 |
| `like` | `momentId` | `{ liked, likeCount, likePreview }` | 明确 toggle 语义，前端不再调用 `unlike`。 |
| `commentCreate` | `momentId`, `content`, `replyTo?` | `{ comment, commentCount }` | 服务端读取当前用户资料、内容审核、写入评论。 |
| `commentList` | `momentId`, `cursor`, `limit` | `{ comments, nextCursor, hasMore }` | 支持详情页评论分页。 |
| `commentRemove` | `commentId` | `{ commentCount }` | 只允许本人删除。 |

服务端负责将 `users`、`figures`、`moment_comments` 聚合为上述 view model；前端不直接拼装 `name/avatar`，也不依赖内嵌的旧 `comments` 字段。对已有 mock 数据写一层 adapter，确保 mock 与线上响应使用相同结构。

### 3. 数据与安全补充

- `moments` 作为官方预生成的古人动态，默认不应由普通用户创建；若开放用户发帖，改为独立的 `user_moments` 或增加 `authorType`、审核状态与可见范围，避免混淆人物官方口吻。
- `moment_comments` 应持久化 `authorSnapshot { name, avatar }`、`replyTo`、`replyName`、审核状态和软删除标记。
- 点赞使用独立 `moment_likes` 时，为 `{ momentId, _openid }` 建复合唯一约束/幂等保障，并将计数异步聚合或事务维护。
- 图片发布须在上传后进行图片安全审核；文字审核失败要明确反馈且不做本地成功提示。

## 六、实施路线

### Sprint 1：先让真实闭环可用（P0，2–3 天）

1. 固化 `MomentView` 和上述 action 契约；同步修正 `moment` 云函数与两个页面的调用。
2. 实现 `detail`、`commentCreate` 前端调用、评论列表查询和 `like` 的一致返回。
3. 移除生产路径的“接口为空即回退 mock”；mock 只在显式开发开关下启用。
4. 完成点赞/评论 optimistic update 的 pending、失败回滚和重试。

**验收：** 断网、接口 4xx/5xx、刷新、重复点赞、从列表进入详情再返回五类路径均不丢状态；开发工具 Network 中不存在 `detail/unlike/comment` 的未知 action。

### Sprint 2：人物与原生朋友圈骨架（P1，3–4 天）

1. 完成人物头像资产首批与 `figure-avatar` 的 error fallback；列表、详情、评论统一使用。
2. 做九宫格、图片预览、文本折叠、头像/名称跳人物页、可定位的操作菜单。
3. 统一详情页和列表页视觉语言；将史实卡收敛为弱层级组件。
4. 替换动态生成封面地址为云存储静态资源，并完善封面加载失败表现。

**验收：** 在 iPhone SE 级窄屏和主流安卓机上，任意动态的操作菜单不遮正文、不越界；所有人物与评论者均有可辨识头像或首字 fallback；1/2/3/4/9 图均正确排版与预览。

### Sprint 3：内容深度与社区治理（P2，3–5 天）

1. 上线朝代筛选、史实出处跳转、评论回复与删除。
2. 增加骨架、空态、失败态和分页加载体验。
3. 明确发布策略；如开放用户发帖，同步完成审核、隐私、举报和管理后台。

**验收：** 用户可从一条古人动态在三步内到达对应人物页或深度文章；所有 UGC 写入均经服务端身份校验与内容审核；空、加载、失败、末页四种状态均有明确 UI。

## 七、发布前检查清单

- [ ] 前端与云函数 action、字段、分页方式有契约测试或最少一份共享 fixture。
- [ ] 线上数据不再静默回退到 mock 数据。
- [ ] 人物、用户、评论三类头像均有加载失败 fallback，且不依赖第三方外链。
- [ ] 头像/姓名、正文、图片、更多菜单、评论回复的点击路径均可用。
- [ ] 点赞、评论在请求失败时可回滚并给出明确提示。
- [ ] 动态图片使用缩略图、懒加载、预览；首屏不加载全量原图。
- [ ] 新增或修改的 UGC 文本与图片均经服务端审核。
- [ ] 真机检查 iOS/Android 的安全区、键盘顶起输入栏、长文本、9 图和弱网。
